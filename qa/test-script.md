# Phase 3 — Test Plan

## Scope decision (stated explicitly, not silently narrowed)

The system has 414 backend endpoints across 56 controllers and 55 frontend routes. A
mechanical application of all 26 API categories × 414 endpoints, or all 20 UI categories × 55
pages, would produce many thousands of test cases — the overwhelming majority of them
near-duplicate CRUD boilerplate (e.g. "missing required field" on 40 near-identical `Create*`
DTOs) that would not be genuinely executed with real evidence in the time available, and would
violate the spirit of "never infer PASS from code inspection" by turning Phase 3 into a listing
exercise rather than a real plan for real execution.

Instead, this plan applies the **full 26/20-category depth to the highest-risk, highest-value
surfaces** identified in Phase 1 recon (the GL/accounting core generally, and specifically the
two defect areas already found in Phase 2 — journal numbering and notifications — plus the
newly-added `InventoryAdjustment`/idempotency features, plus authentication/authorization as
the system-wide concern flagged in `00-recon.md` §8), and applies a **representative
subset** (happy path, key validation, auth boundary) across the remaining modules (catalog,
shops, currencies, orders) to establish breadth without pretending exhaustive depth. Coverage
gaps versus the full 26/20-category matrix are enumerated honestly in `summary.md`, not hidden
here.

All test data referenced below uses the accounts/values recorded in `env-notes.md`.

## Notes on execution approach

- All DB verification steps query the QA MySQL instance directly (`mysql -h 127.0.0.1 -u root pos_system`), not through the application, to avoid a test "verifying itself" via the same code path being tested.
- TC-API-008 (expired JWT) requires crafting a token signed with the real `JWT_SECRET` and a past `exp` — done via a small script using the same HS512 algorithm, not by waiting out a real 24h expiry.
- TC-API-027 (concurrency) is executed with two backgrounded `curl` processes launched as close to simultaneously as shell scripting allows — a real race, not a simulated one.
- Where a test's actual observed behavior differs from what a plausible reading of the code predicted, the **actual, observed** result is what gets recorded — this table's "Expected Result" column states what a correct system should do, not a guaranteed prediction of what this system will do.
